# Investigation Harness  Design Report

## Design Choices and Rationale

**Architecture: hand-rolled loop over an agent framework.** The core is a plain `for` loop in `agent.py`: at each step, an LLM call (`decide_next_step`) decides to search or conclude based on everything gathered so far; the result of that decision is executed, and the outcome is appended to a running `findings_log` that the *next* decision sees. No LangGraph or similar framework was used  for a 48-hour take-home explicitly graded on demonstrated judgment, a transparent, inspectable loop was judged more valuable than framework abstraction, and it made every bug in this project traceable to a specific, readable line of code.

**Search provider: Exa over Tavily, SerpAPI, Brave, Firecrawl, Linkup, and Valyu.** Evaluated against the project's actual constraints  a solo 48-hour build with heavy iterative debugging expected  rather than raw feature comparison. Exa's pay-as-you-go free-credit model gave more headroom for repeated test runs than Tavily's smaller fixed allowance would have; Firecrawl solves a different problem (full-page-to-Markdown conversion) that a plain `requests` + `BeautifulSoup` fetch already covered adequately at this scope; Linkup's benchmark accuracy wasn't worth the risk of a less-established API under time pressure; Valyu's specialized data sources (SEC filings, PubMed) weren't relevant to this project's subject types.

**LLM provider: Groq (free tier) over Anthropic/OpenAI.** Once it became clear the assignment required dozens of LLM calls per investigation (one per evidence judgment, plus one per planning step), a paid API was avoided in favor of Groq's genuinely free, no-card-required tier. Model name is centralized as a single constant precisely because two models used during development (`llama-3.3-70b-versatile`, then `llama-3.3-70b-specdec`) were deprecated by Groq mid-project  this is a real, undocumented risk of building on free hosted-model tiers, and the fix (one configurable constant, not a hardcoded string scattered through the codebase) is a direct response to hitting that problem twice.

**Verdict and confidence as separate fields.** An early version of `ClaimTracker.confidence()` measured only `support_score / total`, meaning a claim disproven by strong, unanimous evidence (e.g. "OpenAI released GPT-5 in 2024") scored **0.0 confidence**  technically because there was no *supporting* evidence, but this reads as "we don't know," when the system actually had a clear, well-evidenced answer ("this is false"). The fix splits the concept in two: `verdict()` determines the direction (`supported`, `contradicted`, `inconclusive`, `insufficient_evidence`), and `confidence()` measures how strongly the evidence leans in whichever direction that is. This is arguably the most important correctness fix in the project  it changes what the confidence number *means*.

**Tiered source reliability, not a binary trusted list.** Sources are scored in four tiers: official/government records (1.0), established media (0.8), business-data aggregators like company registries (0.65), and everything else including a subject's own website (0.4)  deliberately below the midpoint, since self-description is the least independent evidence available. This directly answers the brief's "evaluating evidence and source reliability" requirement with a specific, justified scale rather than a flat yes/no.

**Three-way (four-way) evidence classification.** Evidence is never just "supports" or "contradicts"  it can also be `irrelevant` (mentions the subject but carries no real information) or `ambiguous_entity` (may refer to a *different* real-world entity sharing the same name). Both are excluded from the confidence calculation. This was added after early runs on "Acme Logistics"  a deliberately generic name  kept mixing evidence about what appear to be multiple unrelated companies with the same name into one confidence score.

## Key Findings

**1. Confidence and verdict direction are not the same thing, and conflating them produces actively misleading results.** Documented above  see `benchmark` output for "OpenAI released GPT-5 in 2024" before and after the fix: identical evidence, confidence flipped from 0.0 (misleading) to 1.0 with `verdict=contradicted` (correct).

**2. Long-term memory can introduce investigative bias, not just efficiency gains.** Real example from `logs/investigation_log.jsonl`: after recalling a prior 0.0-confidence investigation of "Acme Logistics Pvt Ltd," the agent's next planning step reasoned *"Previous investigation yielded no evidence... need to assess potential wrongdoing"*  shifting from neutral fact-finding toward fraud-specific search queries (`"...fraud allegations corporate misconduct..."`) with no new evidence prompting that shift, purely because the memory note mentioned low prior confidence. This is a genuine instance of the "harmful or irrelevant memory retrieval" failure mode the brief's metrics section asks about: memory recall changed *what the agent looked for*, not just what it already knew.

**3. Larger, well-resourced subjects are sometimes harder to investigate than smaller ones  the opposite of intuition.** Tata Consultancy Services initially returned near-zero usable evidence (17 tool calls, 0 confidence) while a small, ambiguous company ("Acme Logistics") returned plenty. Cause: TCS's official site sits behind CDN/bot-protection (Akamai edge error pages, `edgesuite.net` responses) that a plain scraper can't get past, while smaller entities' information often lives on less-protected aggregator sites. This is a structural bias of any lightweight-scraping OSINT approach, not a bug specific to this implementation.

**4. Reflection catches real problems, not just generic hedging.** In the final Acme Logistics run, the reflection step correctly identified that a "supporting" source was actually company self-promotion with no factual content (*"the corporate-info sources merely provide basic company data without any mention of wrongdoing"*), directly contradicting the 1.0 confidence the formula had produced. The self-critique step is doing genuine analytical work, not boilerplate disclaimers.

**5. An agent must be prevented from conclusion-without-evidence.** Early runs showed the planning LLM occasionally choosing `"action": "conclude"` on its very first step, with zero searches performed  almost certainly answering from its own training knowledge rather than anything actually investigated. A hard rule was added: the agent cannot conclude while `tracker.evidence` is empty, regardless of what the model's internal knowledge suggests. Every verdict must be traceable to evidence gathered *during that run*.

## Metrics: Formulas and Justification

**Confidence** (`ClaimTracker.confidence()`): reliability-weighted evidence in the winning direction, divided by total reliability-weighted evidence on both sides:
```
confidence = max(Σ reliability(supporting sources), Σ reliability(contradicting sources)) / total
```
Excludes `irrelevant` and `ambiguous_entity` evidence from the calculation entirely  evidence that doesn't actually bear on the subject shouldn't dilute or inflate confidence either way.

**Episode reward** (`compute_episode_reward`):
```
reward = final_confidence − (0.02 × steps_taken) − (total_tokens / 100,000)
```
Rationale: a confident, well-supported conclusion is the goal, but an agent that takes many steps or burns many tokens to reach it is objectively less efficient than one that converges quickly  directly answering the brief's efficiency requirement. Penalty weights are small relative to confidence (max realistic penalty ≈ 0.3–0.4 at `max_steps=6`) so inefficiency discourages waste without letting a fast-but-wrong run outscore a slower, correct one.

**Step-level reward** (`InvestigationMetrics.step_rewards()`): the change in confidence between consecutive steps  a positive value means that step's search/evidence genuinely moved the investigation forward; a value near zero means the step added noise without changing the conclusion. This is the basis for convergence tracking: the TCS benchmark run shows confidence progression `[0.0, 0.0, 1.0, 1.0, 1.0, 1.0]`  flat for two steps, then a single decisive jump once a real financial-results article was found, then stable. That shape  flat, jump, plateau  is what a genuinely convergent investigation should look like, as distinct from confidence oscillating step to step, which would indicate an unstable or confused agent.

**Memory ablation.** `main.py --no-memory` disables recall/save for a single run, allowing direct comparison. The qualitative finding (point 2 above) was more informative here than a quantitative before/after confidence delta, since the memory-bias effect showed up in *search strategy*, not in the final number  a limitation of confidence-only metrics worth naming explicitly (see below).

## Limitations & Future Optimizations

- **JS-rendered and bot-walled pages are inaccessible.** Plain `requests`/`BeautifulSoup` cannot execute JavaScript; sites like `tcs.com`, `gatesfoundation.org`, and Cloudflare-protected pages return either CDN error pages or bot-challenge text, which this system detects via content-length and known-signature filtering rather than actually accessing the real content. A production version would need a headless browser (Playwright/Selenium).
- **Content-emptiness filtering is a growing list of known signatures, not a general solution.** Over the course of this project, five distinct "looks-like-content-but-isn't" shapes were found and patched individually (SSL failure text, soft-404 body text, CDN error pages, bot-wall messages, and marketing copy that mentions the subject without informing about it). Each fix caught the shape that had already been observed; none generalizes to the next one. A dedicated fact-extraction or "is this text actually about X" classification step would be a more principled fix than pattern matching.
- **Entity disambiguation is heuristic.** The `ambiguous_entity` classification relies on an LLM judgment call per piece of evidence rather than any structured entity-resolution (e.g. matching registration numbers, addresses). Generic subject names (like "Acme") remain genuinely difficult to disambiguate reliably.
- **Long-term memory keys on exact subject-string match.** "Acme Logistics Pvt Ltd" and "Acme Logistics" would be treated as unrelated entries. Real entity resolution (fuzzy matching or persistent entity IDs) would be needed for this to scale.
- **Memory-bias risk (Finding #2) is currently unmitigated.** The system detects and reports this bias but doesn't yet correct for it  a future version might prompt the planning step to treat prior confidence as *context* rather than a *lead to pursue*, explicitly instructing it not to let low prior confidence bias query formulation toward a specific hypothesis (e.g. fraud) without new evidence justifying that direction.
- **Confidence-only metrics can miss behavioral effects.** The memory-interference finding was visible in the agent's search queries and reasoning strings, not in its final confidence score  suggesting future evaluation should track query/reasoning content over time, not just the numeric outputs.
